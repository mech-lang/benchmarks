Reviewed 2026-10-20, using the retained sources and `experiments/implementation-audit/v1/inventory.json`. This reviewer ran no BQN, compiler, benchmark or profiler. New nucleotide measurements and work witnesses below were executed by the sole main runner. ## Binary trees

Source: `archive/comparisons/array-comparison/all-20261009/sources/binarytrees.bqn`, SHA-256 `d8b7d5734f2be70b308ecc29c4841f1a5f6c8b7075180a95e8e73e6b18efa378`; selected median30.1465245 seconds, application LOC16. There is no retained compact/optimized two-source contest for this workload: one faithful source is not optimization evidence.

`Tree` recursively calls `Node` twice and allocates an actual boxed pair for every node, including leaves. `Check` creates an Each result for the two children and reduces it at each nonleaf. `Compute` also constructs `iterations⥊depth` and the entire scalar result vector before summing it. Allocation/recursive callback dispatch and those intermediate arrays are source-level hotspot hypotheses. Compare a direct two-child recursive check with the current `+´𝕊¨children`, and a small explicit Node construction versus its helper call. For the independent-tree loop, compare bounded batches (for example256–4096 checks per batch) to retain array expression clarity without an input-sized vector of iteration results. Do not replace checks by the known node-count formula.

Task balance is a concrete gap. At canonical depth21 there are nine depth jobs (4 through20) but eight workers receiving contiguous jobs; one worker receives two approximately equal-cost depth workloads. Split each depth's iteration range into several independent jobs, combine only their real check totals, and compare task counts8/32/72/128 with unchanged allocation/check work. Preserve the parent long-lived tree and full stretch tree. Reusing trees, pooling nodes, sharing leaf nodes or constructing a dense preallocated surrogate changes the [required allocation workload](https://benchmarksgame-team.pages.debian.net/benchmarksgame/description/binarytrees.html). The current four small expression helpers are already a useful compact endpoint; a longer scheduling variant should earn its place through matched results and allocation evidence.

## Fannkuch redux

Parallel source: `archive/comparisons/array-comparison/all-20261009/sources/fannkuchredux.bqn`, SHA-256 `bf4a836b7f4b5d9ba4871e522de5d0d039dee9aadc3b0d9912cceb64ac5e3846`; median164.855024125 seconds, LOC50. Both are local/derived drafts, not newly identified upstream originals.

The parallel source already initializes each worker's first permutation by descending factoradic ranks, uses global rank parity, performs every actual prefix flip, and rotates/carries to its endpoint. `Flip` allocates a reversed prefix and concatenates the untouched suffix on every flip; Carry does another take/rotate/drop/join and indexed Under for the counter. Scalar `•_while_` callbacks and these tiny-vector operations repeat through479001600 permutations. Eight equal rank intervals already have good task-count balance; finer rank tasks are only an experiment in variable flip cost, not an obvious scheduling fix.

Compare prefix reversal/rotation written through Under of Take against the current concatenate form, so CBQN can potentially reuse the evolving temporary flip vector after its first copy. The original permutation must remain available for the next rotation. Static source does not prove that a particular Under expression hits an in-place specialization. Also compare a pair-at-a-time canonical generator with the common first-two swap/rotation ordering seen in retained C/Nim implementations; preserve every permutation, actual flips and exact alternating parity. Keep the existing `Flip` expression function as the compact form. Batching permutations into a huge matrix would multiply memory and does not remove the state-dependent flip loop. ## FASTA

Source: `archive/comparisons/array-comparison/all-20261009/sources/fasta.bqn`, SHA-256 `531d039ae5f9aa34f9db35e4df9efc723dc64098e3b1828c7b4fba972e35085e`; median10.785043417 seconds, LOC24. This is one faithful source; no retained BQN CDF/buffering search establishes that its chosen shape is fastest.

`Random` materializes every state with ``seed Rand` size⥊0``, then a cumulative-probability-by-sample comparison matrix, transposes it and sums rows. At N25000000 the THREE state vector alone has125M elements; the IUB comparison has15 probability rows. A precise idiomatic candidate is `indices ← cumulative ⍋ r÷139968`: [Bins Up](https://mlochbaum.github.io/BQN/doc/order.html#bins) counts sorted thresholds less than or equal to each draw, matching the present `cumulative ≤ draw` boundary convention. This uses the ordinary sorted-search primitive, retains each floating division and draw, and avoids the CDF×sample matrix. Compare it to a flat sequential-threshold accumulation over a bounded draw block; neither has measured superiority yet.

Process multiples-of60 blocks (for example60×4096 through60×65536), carry the actual final LCG state between blocks and both random records, and generate every requested update with the original recurrence. `Wrap` also calls an append-newline function for every60-byte row; compare a native matrix append/transpose or flat gather that inserts newline columns in bulk, with bounded output buffers. Do not expand array operations into scalar code merely to count them. N=0 currently makes `¯1⊑r` invalid, so explicitly handle empty random records before broader admission. Preserve the exact ALU truncation, all200M random draws, float CDFs, seed continuity and final newlines. Period reuse, leap-ahead replacement of the prescribed draws and precomputed output are not proposed; see the [task](https://benchmarksgame-team.pages.debian.net/benchmarksgame/description/fasta.html).

## Mandelbrot

Source: `archive/comparisons/array-comparison/all-20261009/sources/mandelbrot.bqn`, SHA-256 `4b351ad41c01af5ae8ffbd0b993946e0d905718a2a236a65d7af3ba47fa52c4b`; median26.760191542 seconds, LOC21. It operates on a full real/imaginary row, performs50 steps and retains sticky membership. No retained alternate BQN row/tile/packing/parallel design is established.

The step computes squared components to form `rr`, then recomputes both squares for the membership test. Carry `zr²` and `zi²` into the next iteration, updating them once after each new z; this can remove redundant products while preserving the same update/test order. Compare dense tiles of2/4/8 rows to reduce callback dispatch, with cache and temporary-size effects measured rather than presumed. Whole-tile early exit is valid only when all pixels have already escaped; per-pixel active compaction adds gather/allocation work, as the retained MATLAB comparison illustrates.

The byte packer maps a reduction over millions of length-eight rows. The same long-vector Horner technique qualified for nucleotide is a concrete alternative: reversed transposed bit rows inserted with `𝕨+2×𝕩`, producing identical most-significant-bit-first bytes. Compare it independently from iteration changes. Eight language row-range workers are also possible, but the current generic parallel map serializes output through textual `•Repr`; account for that cost or separately review a generic binary transport. Preserve requested dimensions, fifty-iteration boundary behavior, exact PBM bytes and zero tail padding. The current21-line dense row remains the compact endpoint; no lower precision, cached image or native fractal kernel.

## Pi digits

Source: `archive/comparisons/array-comparison/all-20261009/sources/pidigits.bqn`, SHA-256 `1c5f861102122ffab59f27cd6cef72cf0ba38dd3f8e17275e53c67dc5b054eb7`; median0.428152291 seconds, LOC41. It already uses mutable unbounded GMP objects and the accepted q>r guard. The expensive digit algorithm is in BQN; the binding exposes only ordinary arithmetic. Recommending GMP or the guard again would miss what is already implemented.

Hoist frequently read namespace methods outside `Step`/`Extract`, as with the nucleotide Get/Set investigation; this only hypothesizes dispatch savings. More substantial generic arithmetic candidates are `mpz_addmul_ui` for r+=2q and `mpz_submul_ui` for r−=t×d. These are standard [GMP operations](https://gmplib.org/manual/Integer-Arithmetic), not a spigot executor. While evaluating both endpoints, the second numerator can be computed from the already formed3q+r by adding q, followed by a **second actual division**. This removes redundant multiplication without inferring the second digit from a remainder or equality shortcut. Retained C/Nim sources provide concrete addmul/submul patterns.

The current `digits ∾↩` and1000 line writes are secondary candidates: compare a preallocated language-level character result filled by index and batched ten-column output only after profiling confirms allocation/output cost. Do not assert quadratic concatenation without inspecting CBQN's reuse path. Keep the41-line form as an expressive endpoint; fused generic arithmetic may reduce written work as well as dispatch. Preserve unbounded precision, both real endpoint divisions when tested, sequential LFT state, no cached digits and N0/1/9/10/11 formatting.

## Regex redux

Source: `archive/comparisons/array-comparison/all-20261009/sources/regexredux.bqn`, SHA-256 `9e22411c1b3bdf8c575d4560a505bf321957984733cb73f7154c5c94f1cd1e5c`; median2.485554167 seconds, LOC16. It already performs nine independent case-sensitive PCRE2 count traversals and five real sequential substitutions. `regex_new` compiles/JITs a supplied general pattern; this is ordinary library work, not a combined benchmark matcher.

A concrete library hotspot is `native.c:54–64`: each `regex_replace` first calls `pcre2_substitute` to determine exact size, then calls it again to construct output. The wrapper also copies returned bytes into BQN and converts them to characters. Compare a generic reusable/growable output buffer starting near input size, retrying on ordinary overflow, against the present exact-size two-pass API. One prescribed replacement can expand output, so a fixed input-sized buffer without overflow handling is incorrect. This is a separately pinned generic regex-library change with BQN still orchestrating all operations. Independent count patterns can run in up to eight existing language workers, then print results in original order; the read-only DNA is inherited on fork. Nine jobs still give one worker two patterns, and cleaning/substitutions remain serial, so measure whole-program effects and memory. Do not add parallelism around ordered substitutions. The16-line application is already compact; counting its native standard-library calls as hidden benchmark code would be inconsistent with other regex implementations, but adding a native benchmark-specific matcher would change that boundary.

## Reverse complement

Source: `archive/comparisons/array-comparison/all-20261009/sources/revcomp.bqn`, SHA-256 `171d8aaeb599bf62a8a6e6a9ab5a04b7794ba31d5e31386d46acdd2e0a80256b`; median1.022621375 seconds, LOC16. `•FLines` retains the whole input as lines; each Record joins its complete sequence, maps32 upper/lower IUPAC codes through Index Of, reverses, reshapes into60-column rows and appends a newline by rank callback. ### The required work really includes all histograms

The [current primary task description](https://benchmarksgame-team.pages.debian.net/benchmarksgame/description/knucleotide.html) requires a built-in/library hash table, growth from a small default size, and counting all sequences at all seven widths. It explicitly rejects custom hash tables and says: “Don't optimize away the work.” This is an authentic restriction, not an invented local rule. Query-only matching, dense 4/16-element arrays replacing the required hash tables, and counting just the five wanted long strings are inadmissible replacements.

Partition organization is more flexible: the [published Rust #7 source](https://benchmarksgame-team.pages.debian.net/benchmarksgame/program/knucleotide-rust-7.html), `freq` lines 121–137, rolls through every overlapping key into one default `hashbrown` map, rather than constructing a distinct table per reading frame. This supports comparing chunk-map organizations while preserving every key's lookup/update. This is an inference from the published implementation, not an official ruling on a new BQN submission.

### What the retained source already does, and misses

At lines 7–16 it encodes DNA into 0–3 and forms base-4 integer keys, so packed integer representation is **already present**. All keys up to k=18 require 36 bits and are exactly representable as BQN numbers. Each reading frame is divided into eight pieces; a new empty built-in `•HashMap` receives every piece's keys through an interpreted fold with separate Get and Set calls. There are `8×(1+2+3+4+6+12+18)=368` maps and seven batches of eight children, or 56 fork operations. Jobs are frame-major, then piece-major. Each child receives a contiguous batch of `width` jobs, not necessarily one entire frame.

Every width contributes `N-k+1` updates. For THREE length 125,000,000, the total is `7N-39 = 874,999,961`. Encoding currently performs work proportional to `k(N-k+1)` per width: it creates a rows-by-width array, repeats powers across that shape, multiplies, and reduces short rows. The total coefficient across widths is 46, rather than seven rolling passes. Temporary products, short-axis reduction, interpreter calls, generic map storage, and repeated map growth are credible bottlenecks; this review does not identify their measured shares.

The generic process map in `standard.bqn:31–53` runs BQN callbacks in forked interpreters, serializes their results, and waits in the parent. `native.c` supplies POSIX operations and generic library bindings; its existing `map_new/get/set/close` functions wrap khash for K. No nucleotide counting kernel is hidden there.

### Concrete candidates preserving all required updates

1. **Hoist map operations.** Bind `Get ← 0⊸h.Get` and `Set ← h.Set` outside the scalar update fold. The pinned runtime's `src/core/ns.c:47–54` linearly scans namespace field IDs, and `src/vm/vm.c:906–910` performs that lookup for field reads. Hoisting may remove repeated lookup work; compiler optimization could already remove part of it, so measure.
2. **Use long-vector Horner encoding.** Compare line 14 against `keys ← {𝕨+4×𝕩}˝⌽⍉rows‿width⥊data`. Transposition makes each operand a long vector; reversed leading-axis Insert implements big-endian Horner accumulation. Plain Fold `´` on the matrix is invalid: it requires rank one. This reduces repeated weight storage and avoids reducing millions of short rows, but adds a transpose. [Official performance guidance](https://mlochbaum.github.io/BQN/implementation/perf.html) distinguishes optimized flat-list operations from uneven multidimensional optimization; [Fold/Insert documentation](https://mlochbaum.github.io/BQN/doc/fold.html) establishes the reduction semantics.
3. **Chunked composition/rolling keys.** A scalar rolling recurrence is `next=(4×previous+digit) mod 4^k`, after seeding the first k-1 digits; it reduces key construction to O(N) per width but adds interpreted arithmetic if written as a scalar BQN loop. A more array-oriented candidate composes aligned slices: `x2=4*x1+shift1(x1)`, `x3=4*x2+shift2(x1)`, `x4=16*x2+shift2(x2)`, `x6=64*x3+shift3(x3)`, `x12=4096*x6+shift6(x6)`, `x18=4096*x12+shift12(x6)`. Truncate each slice to its valid windows, process bounded chunks with a 17-base halo, and feed **all** resulting keys into growing maps. Avoid retaining seven whole-input vectors unnecessarily.
4. **Compare map partition sizes.** Eight contiguous chunk maps per width reduce map construction and repeated growth but can make each k=18 table about 18 times larger than a present piece table, hurting cache use and memory. More small maps can also reduce residency and be faster. Preserve the same number of updates and audit boundaries; do not presume that fewer maps wins.
5. **Compare a library-backed BQN map.** Bind the existing one-key khash functions from `native.c`. This is allowed by the task's library-table rule and keeps encoding and update sequencing in BQN. It may improve hashing/storage or lose to FFI overhead. Do not add a bespoke nucleotide loop or a custom table, prepopulate keys, or reserve an input-sized table.

### A native built-in accumulation candidate worth a separate work review

Pinned CBQN offers no bulk/increment method on `•HashMap`: `src/builtins/sysfn.c:731–754` exposes only Get/Set/Has/Delete/Count/Keys/Values. `src/builtins/search.c:685–748` shows separate hashes/probes for Get and Set, boxed key/value arrays, a hash/index array, and automatic growth near 7/8 load. Packed numeric atoms already take a scalar `wyhash64` path in `src/utils/hash.h:18–33`; narrowing the temporary key vector does not narrow the map's boxed slots.

However, the built-in occurrence-count primitive `⊒` has a genuine generic hash-table accumulator in `src/builtins/selfsearch.c:387–395`. It allocates `H_b2i` with 64 slots, then calls `mk_b2i` and stores/increments a value for **every** key. `src/utils/hashmapTemplate.h:131–140` proves lookup, insertion, and doubling from that default. Values encode occurrence counts minus one, which the returned ordinals preserve.

Bare packed integers are unsuitable: earlier branches use dense indexing, sorted scans, brute force, or radix fallback. An ordinary list of boxed actual packed keys, `ord ← ⊒ <¨keys`, forces the generic path: the outer array has element type `el_B`; `canCompare64_norm` rejects that type, so no integer dense/64-bit fast path applies. Boxing the actual DNA rows, `⊒ <˘rows‿width⥊data`, is another structural-key candidate. Neither needs an artificial extra key field. The latter hashes more data.

After every key was accumulated, extract results from the ordinals. For a long wanted key: `⌈´ 0∾1+(keys=wanted)/ord`. For k=1,2: `(4⋆width)↑0⌈⌈´¨ keys⊔1+ord`. Grouping is only postprocessing the completed hash counts. Existing sums across Frame results remain valid. A simple reference extraction can scan each of the four/sixteen keys with the same max formula.

This preserves the substantive native hash-table work and is a plausible interpretation of “built-in ... hash table implementation”; it does not expose a public HashMap object. Admission therefore needs an explicit work review and evidence, not a claim that any `⊒` implementation is automatically acceptable. In particular, `count_c1:293` bypasses all tables for zero/singleton inputs: singleton pieces need an ordinary HashMap fallback if strict work parity is required for tiny fixtures.

An untimed instrumented witness can record generic-path invocations, input element type, initial/final slots, unique keys, and actual loop updates before the map is freed. The full total must be 874,999,961; N=1000 FASTA gives THREE length 5000 and total 34,961. Include all seven widths, repeated keys, growth, and the singleton fallback. Debug evidence must be separate from the unchanged timing executable.

### Correctness and workload traps

- Count overlapping windows across FASTA line and chunk boundaries; discard halo-started keys belonging to the next chunk. Carry/seeding requirements depend on the chosen encoding direction.
- Preserve case handling, CRLF behavior, stop at the next FASTA header, and no-final-newline input. Keep line-by-line input semantics; replacing parsing with whole-file mapping would require its own task review.
- Clamp frame window counts for N<k; the present `floor((N-frame)/width)` can become negative on tiny inputs. Test zero-length/singleton pieces and counts at every reading frame.
- Unknown DNA characters currently map to A because index-not-found is 8 and `4|8=0`; generated workload DNA uses A/C/G/T. Do not silently broaden claims to ambiguous FASTA alphabets.
- Preserve descending frequency with ascending lexical key on ties. Current increasing ACGT packed keys plus stable Grade Down give that ordering; [BQN ordering documentation](https://mlochbaum.github.io/BQN/doc/order.html#stability) specifies stability.
- Built-in `⊒` count values are 32-bit; canonical per-piece counts fit. Key arithmetic needs all 36 bits at k=18. Do not truncate through 32-bit bit casts; BQN's bitwise 64-bit result representation has special float-bit semantics, so ordinary numeric arithmetic is the safer first candidate.
- Correct stdout alone does not establish required hash work. Keep source, runtime, partition, output, and work witnesses attached to any newly admitted candidate; retain the old sources and measurements unchanged.
