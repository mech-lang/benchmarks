# Ruby source review, ten workloads

This is a read-only review of the protected, unchanged Game sources in the catalog: 19 distinct files, 23 Ruby/YJIT labels and 19 ZJIT labels. Runtime aliases are not new implementations. The fresh YJIT regex/pi profiles and first-call Fannkuch profile retain their original source hashes; all ZJIT labels alias those same 19 sources. No source edit, conformance re-admission or new timing is proposed here. The completed CRuby 4.0.7 ARM64 YJIT/ZJIT runtime study is documented in `docs/ruby-jit.md`; it should not be repeated as an application optimization. All observations below concern written source and retained measurements, not new profiling evidence.

| Workload | Source assessment and remaining research question |
| --- | --- |
| n-body | Ruby-2 (110 retained LOC, 59.954 s) and Ruby-3 (113, 56.653 s) use Planet objects and inline the hot pair operations. Ruby-3 already reuses squared distance times its square root and an `add_v` method. Coordinate arrays are a distinct future experiment, not an assumed win; object/float allocation costs need runtime evidence. Both original files remain protected. |
| Mandelbrot | Ruby-8 (38, 280.739 s) is a compact scalar implementation; its inner fixed loop keeps visiting iterations after the escape flag clears. Ruby-5 (122, 33.545 s) breaks on escape, packs rows and uses a generic fork map. Early escape and parallel rows already exist in the submitted pool. Process-copy/serialization costs remain a runtime question; no symmetry or interior shortcut is implied. |
| k-nucleotide | Ruby-2 (31, 88.774 s) slices string keys into Hash counts and enumerates all windows through strided frames. Ruby-1 (50, 24.768 s) forks seven arbitrary block workers, one for each frequency/query length, and builds the complete per-length map with a lookup/update per window. Rolling packed keys are a different future source implementation. The original `^>THREE` prefix handling and absent-record behavior stay unchanged; a stricter newly authored admission rule must not silently rewrite or retroactively invalidate a protected upstream submission. |
| spectral norm | Ruby-8 (29, 47.873 s) is scalar and packs several independent statements with semicolons. Ruby-5 (95, 19.606 s) already runs generic six-worker maps for the dense products and serializes ordered results. All 40 products remain visible; repeated worker creation/Marshal crossings are a concrete source-level cost hypothesis. A persistent general worker pool is a possible future runtime/library experiment, not a cached matrix or native workload executor. |
| reverse complement | Ruby-5 (15, 1.413 s) reverses/translates record segments and writes 60-byte lines. Ruby-4 (57, 0.694 s) forks record work and bridges completion with threads, materializing an output string. Both include U/u in the complement mapping. Bounded record/block I/O would be a separate source experiment; the retained original bridge is coupled to the workload method and is not automatically reusable support. |
| Fannkuch redux | Ruby-8 (46) calls its compact permutation kernel once; the completed runtime study found 1079.7 s under default YJIT and 316.7 s with first-call compilation. Ruby-2-cpu4 (174, 68.744 s) already uses reusable scratch arrays and weighted permutation chunks over four generic workers. Initialization advances through `start.times { permute }`; rank unranking could change startup work but requires a separately admitted source. The weighted chunks, actual flips, checksum/max merge and platform branches remain application logic. |
| FASTA | Ruby-2 (66, 34.762 s) accumulates random output in a large string and searches the CDF linearly. Ruby-6 (95, 11.171 s) already reuses a 60-character buffer, uses `setbyte`, and generates a CDF-specific `map_value` method with `instance_eval`. Each draw still advances the LCG and performs the required floating division; seed continuity remains source-visible. Generated method construction is application preparation inside the process timing, not generic excluded support. No periodic-output cache is proposed. |
| binary trees | Ruby-1 (27, 22.222 s) and Ruby-5 (117, 7.221 s) construct/check fresh two-element nested arrays. Ruby-5 already distributes depth jobs through MiniParallel. Both release the stretch root and retain the long-lived root; no sharing, flattening or closed-form replacement is an equivalent optimization. Per-depth callback orchestration remains counted outside the generic worker module. |
| regex redux | Ruby-3 (74, 4.415 s in fresh YJIT) joins input lines, uses block `scan` to avoid a match-result array, and starts nine forked count workers under CRuby. Ruby-9 (23, 11.369 s) uses case-insensitive patterns and materializes `scan` results, with serial counts and the five replacements. These are unchanged upstream sources; keep their original flags and admission. Match allocation/engine work is a plausible explanation requiring profiling, not evidence that JIT can replace native regex matching. The fixed `original_pattern_count` fork bridge is deferred from support exclusion. |
| pi digits | Ruby-1 (69, 4.915 s in fresh YJIT) represents q/r/s/t transformations as objects, creates composed transformations, and performs both extract-3/extract-4 integer divisions. Its recursive `next!` consumes terms until stable. A GMP-enabled Ruby runtime is a runtime-build question (the studied installation records `--without-gmp`), not permission to rewrite this original as a native pi executor. |

The retained seconds above identify the published YJIT source profile or its explicitly fresh timing alias. They are not cross-runtime universal performance claims. ZJIT is independently timed, and first-call YJIT is a separate execution variant, not a hidden warmup. The completed runtime study reports ZJIT slower in most workloads, with reverse-complement close enough that it should not become a blanket engine recommendation.

Source-size boundaries need their own review. The complete MiniParallel modules in trees, Mandelbrot and Fannkuch and generic Worker classes in spectral norm and k-nucleotide are currently counted in application source. A separate exact-hash proposal in `experiments/source-normalization/ruby-support-v1/` reviews only those definitions; it preserves imports, workload argument parsing, chunk construction, callback bodies, reductions and output. It affects ten aliases if approved, changes no source or historical timing, and supplies no unqualified Ruby-native LOC deduction. Existing compact semicolon rows also show why retained lexical LOC must not be advertised as the new Python/Julia native owner policy.

The source metrics Data table and inspector now provide submitted/application/excluded byte, gzip and pinned BPE measures. This is useful evidence, but table/export alone does not let readers compare expressiveness and speed under those alternative measures. Application byte/gzip/BPE chart axes should each select their own per-workload minimum and fewest-source endpoint, leaving times and their fixed baseline unchanged. BPE remains vocabulary/Unicode dependent and gzip remains formatting/repetition dependent; neither is a uniform logical-source measure. The separate native owner qualification stays a reviewed subset until broader parser evidence exists.
