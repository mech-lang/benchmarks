# Standalone AOT execution of source map counting

The complete FASTA nucleotide program in `knucleotide-source-map.mec` expresses counting through Mech state transitions, direct map membership, indexed lookup, scalar increment and pure insertion. Its frequency formatting and query output also remain in Mech. It contains no histogram call. This is a compiler qualification candidate, not a new benchmark admission.

The public CLI built compiler revision `f6fb76f5f284b8731368a5d30028cc1663c2bb03` from a clean checkout, then compiled both source and its encoded bytecode through the Cranelift release application path. Both builds produced the identical standalone executable SHA256 `a7c22076b2a3e65d5c84e1d616ac2cc5d263e26121536add1c9b64cfa03a0398`. The runtime Rust libraries and launcher are release builds; the build CLI itself uses the development profile. The frozen historical release CLI was not overwritten.

All fourteen bounded output cases pass an independent reference: seven inputs for each source/decoded executable, including empty/missing records, header boundaries, lowercase text, CRLF, repeated keys and the full eighteen-character query. Both binaries reject missing stdin and stdout grants without publishing output (four denials), including when an environment variable attempts to request trusted operation. This is the production secured launcher; explicit same-binary secured/trusted benchmark-policy qualification remains separate.

Every successful process receipt reports native AOT, no JIT, no source parser, no resident body evaluation and completed shutdown. Selected window histogram/query regions are both zero, and execution receipts report zero updates through the fused hash-table accumulator. These checks distinguish the source-written state machine from the older histogram path. Ordinary canonical maps do not establish the physical hashing required by the workload; hash storage/entry support, ownership optimization and complete-input work qualification remain pending.

One exported metadata field at the qualified revision incorrectly named the available hashbrown accumulator even when no window region was selected. The zero region counts and runtime receipts remain the authoritative evidence for those builds. Follow-up compiler revision `c303620e657af9a856f01d660654fc368813c0b6` emits null for that field when no accumulator is selected. Its focused check emits original/decoded objects both with and without actual window accumulation, and reruns the 42-case native state-machine test. This metadata correction changes no object-emission or execution algorithm.

`build_cli.py`, `qualify.py`, process receipts, complete launch policy, manifests and application reports retain the build/execution evidence. `seal.py --check` verifies the pinned revisions and results. All subjects execute serially under the existing shared mutex, with owned-process cleanup and finite limits. No quantitative timing samples or canonical dataset rows change.
